00

核心结论：自进化不是“让模型自己改提示词”

一个 SDD Harness 的自进化系统，本质上是把 Agent 的使用过程变成可观测、可复现、可归因、可回归、可灰度的软件工程系统。模型改写 Skill 只是其中一环；更关键的是背后的证据链和发布控制。

判断 1

先做“证据链”，再做“优化器”

没有 Skill 版本、模型版本、工具输入输出、环境状态、测试结果和用户反馈，LLM 提出的修改只是猜测。自进化的第一公民不是“自动改 prompt”，而是可审计的轨迹与实验。

判断 2

不要追求轨迹逐 token 复现

编程 Agent 有随机性、网络工具、文件系统和外部服务。更现实的目标是语义复现：同一入口、同一环境、同一版本、同一评测协议下，多跑若干次，统计任务完成率、门禁通过率和失败模式。

判断 3

Skill 单测好不等于系统更好

Skill 是流程组件，不是孤立函数。单点验证必须和反事实 Harness 评测结合：同一批任务分别跑 old skill / new skill / no skill / skill + gates，观察局部收益、全局成本、副作用和回归。

五个痛点对应策略
痛点核心策略
模型随机、轨迹长、难沉淀版本化快照 + 语义回放 + 多次采样 + 稳定不变量 / 门禁
单点 Skill 数据集和验证贵从真实轨迹聚类造数据 + Skill Contract + Harness 反事实开关
无标签 bad case 难发现硬失败 + 用户编辑/回滚/追问 + 批评模型 + 不确定性 + 抽检
验证集过拟合训练/验证/冻结测试分离 + 时间外测 + 灰度 + 回滚
大 Skill 小收益被噪声淹没模块化 + 局部评测 + 大样本配对实验 + 阈值与效应量
最小可行闭环
  1. 采集：任务、环境、Skill 版本、模型版本、工具事件、测试、用户动作。
  2. 标注：自动失败信号 + 人工轻量标签 + 批评模型评估。
  3. 归因：区分指令、Skill、工具、环境、门禁和模型能力问题。
  4. 实验：构造可重复任务包，配对比较新旧版本。
  5. 发布：shadow → 灰度 → 全量，并保留回滚与监控。
一句话总结：把 Harness 看成“工厂 + 质检 + 试车场”，把 Skill 看成“岗位 SOP”。自进化不是每次让模型重写 SOP，而是持续收集不合格品，定位工序问题，用可控实验验证新 SOP 是否真的提高整条产线的良率。
01

概念与类比：Harness、Skill、轨迹到底是什么

不同团队对 Harness 和 Skill 的定义不完全一样。为了避免讨论漂移，这里采用一个偏工程实践的划分：Harness 负责把模型能力变成稳定交付流程，Skill 是其中可复用、可版本化、可评测的流程资产。

Harness

运行时 + 工作流 + 护栏

包括提示模板、上下文管理、工具调用、沙箱、测试命令、审批流、权限、重试策略、日志、反馈入口和发布机制。它决定“模型在什么约束下工作”。

Skill

可复用的专家流程包

不只是一段长 prompt。成熟的 Skill 应包含：适用条件、输入输出、操作步骤、禁忌、脚本、示例、反例、验证方式、失败处理和版本号。

Trajectory

任务从请求到交付的因果链

包括用户目标、计划、检索、编辑、命令、测试输出、门禁、修复、最终 diff 和用户后续行为。轨迹的价值不是保存所有 token，而是保留可归因的因果节点。

通俗类比：如果把 Agent 任务看成一次餐厅出餐，模型是厨师，Harness 是厨房流程和监控，Skill 是某道菜的 SOP，工具是灶台和厨具，门禁是出餐前质检。坏一道菜不能只骂厨师，还要看菜单是否清晰、食材是否备齐、质检是否能拦住问题。

示例推演：一次真实的失败如何变成进化资产

假设用户提出一个很常见的工程任务：“购物车叠加优惠券后金额算错了，请修复。” Agent 最终跑过了部分测试，但用户发现满减和限时折扣的叠加顺序仍然不对。下面把这个过程拆成七个阶段，展示如何从一次失败沉淀出可复用的回归资产。

第 1 步：记录“原始事实”，而不是只记录聊天

任务开始时保存仓库 commit、目标需求、相关测试、Skill 版本、模型版本、温度、工具白名单、环境变量掩码和门禁配置。不要只保存最终 prompt 和模型回复。

第 2 步：把轨迹切成因果节点

理解需求 → 定位 cart.ts → 阅读 pricing.md → 编辑三处 → 跑 unit tests → 失败 → 二次编辑 → 通过现有测试 → 提交 PR。 每个 Span 记录输入摘要、输出摘要、工具结果、耗时、token、状态和父节点。

第 3 步：捕捉弱失败信号

现有测试通过，但用户 12 分钟后评论：“满减要先于会员折扣吗？”并手动修改 diff。这是典型弱 negative：CI 没红，用户行为却说明交付不完整。

第 4 步：提炼最小任务包

从仓库提取一个最小复现：输入三种优惠组合、期望金额和反例。例如“满 100 减 20 + 9 折 + 运费 5 元”必须规定折扣基数和顺序。把它变成带断言的 fixture，而不是一段自然语言描述。

第 5 步：做多路归因

同一任务包分别执行：old skill、new pricing skill、no skill、new skill + order gate。如果 old skill 在 20 次里 14 次遗漏叠加顺序，new skill 18 次正确但多读 2 个文件，就能同时看到收益和成本。

第 6 步：把教训写进不同层

Skill 增加一句“先列出优惠应用顺序，再实现”；工具层生成“优惠顺序表”；门禁新增“优惠叠加顺序快照测试”。只改 Skill 是不够的，因为模型可能理解了但仍忘记执行。

第 7 步：纳入回归集并灰度

任务包进入 pricing 回归集，同时与库存、退款、税率等任务隔离。新 Skill 先 shadow 跑 3 天，再对 5% 流量灰度。若测试通过率上升、额外 diff 和耗时未恶化，才扩大发布。

常见误区：只保存用户原始需求和模型最终答案，会把后续归因变成“读小说”。如果缺少中间工具状态和版本号，模型随机性一高，团队就会反复争论“到底是 prompt 不好、模型不好、环境不对，还是评测太苛刻”。
03

总体架构：一个可持续进化的 Harness 控制回路

自进化系统建议拆成六个平面：运行时、观测、证据库、归因、实验、发布。这样每个组件可以单独演进，不会把所有逻辑塞进一个巨大的 prompt 或一个巨大的 Skill。

轨迹必须保存的最小字段

类别字段为什么重要
任务task_id、需求原文、任务类型、复杂度用于分层回归，避免把简单任务和复杂任务混算
版本Skill、Prompt、模型、工具、依赖、门禁没有版本矩阵就无法归因
环境repo commit、依赖锁、OS、环境变量掩码、测试 fixture编程任务的失败经常是环境差异
过程计划、检索、编辑、命令、工具输入输出、异常定位“没看需求”还是“工具结果不可靠”
结果测试、lint、构建、diff、审查意见、人工动作硬结果加软反馈才是完整质量
成本token、调用数、耗时、重试、外部工具成本避免 Skill 收益被成本和时延吃掉

每个 Skill 都应有“Skill Contract”

  • 适用范围：何时触发、何时不触发、和哪些 Skill 冲突。
  • 输入输出：需要哪些上下文，产出什么计划、代码或报告。
  • 流程不变量：例如必须先跑测试、必须列出风险、不得改动无关文件。
  • 证据要求：结论必须引用文件、测试或工具输出。
  • 失败处理：工具失败、测试失败、需求歧义时如何降级。
  • 评测集：golden、扰动、对抗、集成和线上任务分层。
  • 健康指标：一次通过率、门禁通过率、额外 diff、人工修改率、成本。
架构启示：不要把“进化”实现成一次性大重写。更稳的方式是把 Skill 拆成多个可验证单元：策略、流程、检查表、示例、脚本和门禁。优化器只能提交小步变更，并由 Harness 决定能否合并。

痛点 1：模型随机、轨迹很长，怎么沉淀与复现

编程 Agent 的失败往往不是单步答错，而是一串状态迁移走偏。因此不应该问“这次轨迹能否一字不差复现”，而应该问：同一任务包、同一版本组合、同一评测协议下，失败模式是否稳定出现？修复后关键失败率是否显著下降？

方法 1

三层复现，不追求伪确定性

精确复现只适合工具结果和环境完全可控的片段；语义复现保留输入、环境和断言，允许路径不同；统计复现则重复 N 次看分布。对编程 Agent，绝大多数优化应使用后两者。

方法 2

把轨迹压缩成因果切片

长轨迹不要整段塞给优化器。先抽取出“任务歧义、关键检索、首次编辑、测试失败、错误修复、用户修改”等决策切片，再保留必要前后文。这样优化器看到的是证据，不是冗长日志。

方法 3

把 bad case 变成不变量

例如失败模式是“改了实现但没更新迁移脚本”，就沉淀成门禁：schema 改动必须伴随 migration；“异常被吞掉”沉淀为 lint 规则或测试。模型不可靠的地方，应尽量转成确定性护栏。

推荐流程：从“一次失败”到“可发布证据”

阶段要做什么产出
1. 快照 保存任务、仓库 commit、依赖锁、Skill/Prompt/模型版本、工具定义、门禁配置。 可审计的 Run Envelope
2. 切片 识别关键事件、错误邻域、状态迁移、首次偏离点。 因果轨迹图
3. 造例 生成最小 repo fixture、输入输出、反例、验收测试和禁止事项。 Regression Task Pack
4. 重复 新旧版本各跑 N 次，固定任务和门禁，记录一次通过率、最终通过率、成本。 通过率分布与失败簇
5. 门禁 把可确定性检查的部分从 prompt 移到 lint/test/review 规则。 可执行护栏
6. 归档 记录修复假设、实验结果、副作用、发布范围和回滚条件。 可追溯变更说明

坏 case 沉淀模板

  • 任务指纹：需求类型、仓库结构、涉及模块、历史相似任务。
  • 最小上下文：相关文件、测试、命令、错误日志，而不是整个仓库。
  • 验收标准：必须通过、必须产出、禁止改动、最大成本。
  • 反例：看似相近但不应触发同一 Skill 的任务。
  • 失败签名：例如“只修 happy path”“跳过 migration”“反复尝试同一命令”。
  • 关联门禁：如果规则可静态化，就转为 lint/test/checklist。

随机性下的评估规则

  • 核心 Skill 至少跑 10-30 次，不要用单次成败下结论。
  • 同时报告一次通过率、最终通过率、重试成本和人工修改率。
  • 报告失败簇分布，不只报告总分。
  • 新旧版本使用同一批任务做配对比较。
  • 给每类任务设置噪声基线；提升小于噪声带时不要宣称有效。
  • 小样本时优先看“严重失败是否消失”，而不是只看平均分涨了 1%。
落地建议：把“复现”重定义为“可检验”。逐 token 复现对模型和应用都太脆；真正要复现的是环境、任务、断言和失败模式。bad case 沉淀的终局不是一段长日志，而是一个能进 CI 的任务包和一组门禁。

痛点 2：单点 Skill 造数据贵、测得贵，还可能全局变差

单点 Skill 的正确验证不是“把 Skill 单独跑一遍”，而是把它放进一个可切换的 Harness。局部分数回答“这个能力是否学会”，系统分数回答“整条 SDD 流程是否更好”。

问题拆解

单点有效、全局失效的四种原因

  • 目标错位：Skill 优化的是“解释质量”，Harness 需要的是“可合并补丁”。
  • 上下文挤占：Skill 太长，挤掉了需求、代码、测试或工具结果。
  • 流程冲突：新 Skill 要求先写设计，旧门禁却立刻要求跑测试。
  • 触发过宽：在不需要该 Skill 的任务上也启动，带来额外步骤和噪音。
设计原则

Skill 评测金字塔

  • 契约测试：是否在正确场景触发、输出是否满足结构、是否尊重禁忌。
  • 能力测试：小型 fixture 上检查核心判断和产出质量。
  • 流程测试：与工具、门禁、审批、重试策略组合后是否顺畅。
  • 系统测试：完整 SDD 任务上的成功率、成本、时延、人工修改率。
  • 线上对照：shadow 或灰度流量验证真实分布。

降低数据集构造成本：不要从零标注，要从轨迹中“挖矿”

数据类型来源用途成本
失败簇真实轨迹按错误签名聚类发现高频问题和 Skill 缺口低
边界例触发 / 不触发 Skill 的相似任务训练路由和防止过度触发低-中
扰动例修改需求、文件顺序、测试名、目录结构检验稳定性和泛化低
对抗例含冲突需求、过期文档、误导性注释检验不盲从和风险识别中
黄金例人工确认的代表性任务发布门禁和长期基准高，但要少而精
线上影子任务真实流量，不返回给用户发现分布漂移中-高

一个实际对照方案

以“代码审查 Skill”为例。单独测它时，模型给出的风险点更全面，评分从 72 涨到 86。但放进完整 SDD 流程后，Agent 可能在每个小改动上都执行长审查、重复请求上下文、甚至为风格问题阻塞合并。因此实验应同时记录：

指标old skillnew skill解读
审查质量评分7286单点能力提升
任务最终一次通过率68%61%可能过度审查或阻塞流程
平均 token / 耗时18k / 7 分钟27k / 11 分钟成本明显上升
人工修改 diff 行数3529产出质量略好
小改动误触发率12%38%需要收紧触发条件

此时正确动作往往不是全量启用新 Skill，而是把它拆成快速审查和深度审查，根据 diff 行数、模块风险和历史失败率路由。

降低验证成本的三个手段：
  1. 先跑便宜判据：Skill 是否触发、输出是否合法、是否越过禁忌。
  2. 用小环境复用缓存：同一仓库骨架、同一依赖层、同一测试快照。
  3. 只对可疑样本做全流程重放；正常样本用抽样和分组指标监控。
结论：Skill 必须自带契约和评测集，但发布决策要看系统指标。若一个 Skill 在局部涨分却增加全流程成本、误触发或与其他 Skill 冲突，就不能直接合并。

痛点 3：线上数据没有标签，bad case 从哪里来

编译失败只是最便宜的显式信号。真实 bad case 通常表现为“没失败但用户不放心”“能跑但不符合架构约束”“第一次跑对但成本过高”。应该建立一个多源证据系统，把硬失败、软反馈、过程异常和模型不确定性组合起来。

1. 硬失败 构建、lint、单测、集成测试、类型检查、部署、权限、沙箱、工具调用超时或异常。
2. 用户软反馈 拒绝、撤销、回滚、手动改 diff、追加澄清、重复请求、复制部分答案后自己修、明显延长会话。
3. 过程异常 重复执行同一命令、反复改同一行、频繁切换方案、读取过多文件、生成超大 diff、绕过测试、多次触发门禁。
4. 语义不一致 实现与计划偏离、忽略测试、结论缺少证据、两次采样给出相互矛盾方案、批评模型和执行模型分歧。

比“点赞/点踩”更有效的用户信号

信号可能含义采集方式
手动修改 Agent diff方案接近但不可直接接受对比提交前后 diff，计算修改比例和语义类型
马上追问澄清需求理解或方案解释不足标记任务分段与用户输入类型
撤销 / 回滚 / 切分支强烈负面信号接入 Git 事件和 UI 操作
把测试改松Agent 可能绕过约束静态 diff 检查测试断言强度
复制到外部工具当前 Harness 体验不足复制事件 + 后续任务关联
长时间无下一步解释不清或用户失去信心空闲时长、滚动、展开/折叠行为

这些信号单独看都有噪声，但可以组成风险分：例如“测试通过 + 用户修改 40% diff + 新增 3 个追问 + 后续回滚”应进入人工标注队列。

无标签数据的主动学习策略

  1. 不确定性优先：多次采样结果分歧大、模型自报置信度低、门禁分数贴近阈值。
  2. 新颖性优先：任务聚类中出现新需求类型、新模块、新错误签名。
  3. 影响面优先：核心服务、迁移脚本、支付、权限、并发、安全相关任务。
  4. 成本异常优先：token、耗时、工具调用数显著超出同任务分位数。
  5. 对照抽样：始终保留一部分随机样本，防止只标注极端 case 导致分布偏差。
  6. 负样本挖掘：成功轨迹里也可能存在“侥幸通过”和“过度工程”。

自动评价器应分层，不能只靠一个“LLM 裁判”

层评价器优点风险
可执行验证构建、测试、类型、lint、安全扫描便宜、稳定、可复现覆盖不了需求和架构
契约检查输出结构、必填字段、权限、禁止文件能发现流程违规规则需维护
过程检查计划一致性、循环、死胡同、工具依赖解释“为什么慢或错”阈值易误伤
LLM Critic需求覆盖、风险识别、可维护性、测试质量覆盖软质量偏长答案、偏表面、易被操纵
Pairwise Judge新旧结果对比适合版本升级位置偏差、长度偏差
Human Audit抽样和争议仲裁校准其他评价器贵、慢
注意 Goodhart：一旦所有优化都朝着“让 LLM 裁判满意”，Skill 可能学会写更漂亮的解释而不是更好的工程交付。因此裁判分数要和测试、用户修改率、成本、后续故障一起看，并定期用人工标注校准。
实操建议：先做三类最小闭环：可执行失败自动入库；用户回滚/大幅改 diff 自动入队；LLM 批评模型对高价值流量按 rubric 打分。其余轨迹只保留统计特征和可检索原文，等出现相似失败簇再回看。
07

痛点 4：从 v1 到 v2，如何迭代整个流程且不过拟合验证集

当你根据一段时间轨迹生成 v2，并在验证集上看到高分时，先不要直接发布。验证集已经参与了“选版本”这个动作；如果每轮都向同一个集合优化，它就会逐渐从测试题变成训练题。正确做法是把数据治理、实验治理和发布治理分开。

数据治理

分层、分时间、防泄漏

按任务族、仓库、用户、时间段切分，而不是按单条轨迹随机切分。同一个事故的不同表述、同一仓库的重构任务，不能同时落在训练集和测试集。

实验治理

冻结测试 + 预注册指标

冻结测试集不参与任何模型或 prompt 的迭代决策。发布前提前写清主指标、护栏指标、最小提升、最大回退和样本量，避免事后挑好看指标。

发布治理

Shadow、灰度、回滚

新版本先不接用户，影子运行对比轨迹；再小流量灰度，观察后续修复率、回滚率和成本；任何护栏指标劣化自动暂停。

推荐的数据池划分

池用途更新频率关键约束
Discovery / Train挖掘失败模式、生成候选 Skill、构造任务包持续更新可自由分析，但不做最终判断
Selection Dev在多个候选版本中选择周期性轮换会被反复使用，分数会乐观
Frozen Test发布门禁长期冻结禁止根据它的结果继续改 prompt
Out-of-Time检验时间漂移每次发布使用后续时间段不能与训练期事故同源
Out-of-Distribution检验泛化定期扩充覆盖新仓库、新语言、新任务族
Online Canary真实流量验证每次发布观察延迟效应和用户后续行为

发布门禁示例

类型指标示例阈值
主指标一次通过率 / 用户接受率相对提升 ≥ 3%，且置信下界为正
质量护栏严重失败率、回滚率、后续 hotfix 率不得劣化超过 0.5%
流程护栏循环率、门禁失败次数、无关 diff 行数不得显著上升
成本护栏token、耗时、工具调用数P95 增幅 ≤ 10%
安全护栏危险命令、权限、秘密泄露、依赖变更零容忍或必须人工审批
稳定性多次采样方差、极端失败比例失败尾部的 95 分位不得恶化

如何周期性迭代而不是“背模考题”

  • 每轮只允许有限次访问验证集；记录每次选择和理由。
  • v3 的训练期必须晚于 v2 的验证期，避免未来信息泄漏。
  • 保留一个至少数月不动的“古老测试集”，检验长期遗忘。
  • 定期加入新仓库、新框架和新任务族，但不要立刻删掉旧挑战。
  • 对被频繁选中的任务降权或 retire，防止变成隐式训练集。
  • 维护 Champion / Challenger：线上持续跑少量 challenger，观察长期差距。

候选版本的合并策略

  • 小步合并：一个候选只包含一类可解释变更。
  • 冲突检测：检查是否与现有 Skill、门禁和审批策略矛盾。
  • 组合验证：A、B 单独有效不代表 A+B 有效，必须测组合。
  • 回滚单元：Skill、Prompt、工具描述、门禁分别可回滚。
  • 版本说明：记录假设、适用范围、已知风险和失效条件。
结论：验证集分数只决定“是否值得继续”，不决定“是否上线”。上线由冻结测试、时间外测、shadow、灰度和长期监控共同决定。
08

痛点 5：大 Skill 里的小改动，收益小、噪声大怎么办

一个 20,000+ token 的 Skill，往往已经从“指令”变成“巨型说明书”。此时单条 edit 的边际收益很容易被采样噪声、上下文稀释和任务异质性掩盖。处理方式不是更用力测一次，而是降低上下文负担、缩小实验粒度、放大有效样本量，并明确“多大差异才值得发布”。

诊断

大 Skill 的常见症状

  • 重要约束埋在中间，模型只记住开头和结尾。
  • 大量通用解释挤占任务特定上下文。
  • 不同章节互相冲突：有的鼓励探索，有的强调不要过度设计。
  • 任何小改都可能影响所有任务，难以定位回归。
  • 评测成本高，团队只能跑很少次，于是把噪声当效果。
解法

把“说明书”改成“运行时知识包”

  • 入口卡：只保留适用条件、核心流程和红线。
  • 模块卡：按场景加载，例如迁移、性能、安全、测试修复。
  • 脚本 / 模板：可确定执行的检查不要用自然语言描述。
  • 示例库：正反例按需检索，而不是常驻上下文。
  • 门禁：用 lint、测试和审查规则拦截已知错误。

小效应评测：先测噪声，再测收益

步骤做法示例
1. 定义最小关心差异 提前确定多大提升才有工程意义，不看统计显著就合并。 一次通过率至少 +3%，严重失败 -1%
2. 测 baseline 噪声 同一版本重复跑多次，得到自然波动区间。 20 次结果为 70%-80%，说明 ±5% 内差异不可信
3. 配对实验 同一任务、同一环境、相近预算下跑 old/new。 只比较每个任务对的成败和成本差
4. 分层汇总 按任务族、模块风险、仓库规模分别看。 大仓库 +5%，小仓库 -2%，不应平均后掩盖回退
5. 看尾部 报告 P95 耗时、最差失败、重复循环率。 平均分提升但极端失败更多，仍不能发布
6. 组合消融 关闭其他 Skill 或固定相邻步骤，隔离新增 edit。 验证收益来自新章节，而非 prompt 顺序变化

统计上的低成本做法

  • 不要只跑一次；对核心路径至少 20+ 次，探索性任务可先 5-10 次筛查。
  • 优先使用配对差值，因为任务难度造成的大量方差会被抵消。
  • 用 bootstrap 计算置信区间，而不是只比较两个平均分。
  • 保留连续指标：人工修改比例、门禁次数、token 成本，不要只看成败。
  • 把“临界成功”标为 uncertain，避免侥幸通过污染结论。
  • 小收益只有同时具备“低风险、低回退、可组合”时才考虑灰度。

工程上的替代方案

  • 确定性化：把重复出现的规则改成脚本、模板或 hook。
  • 分层加载：默认只放入口卡，子流程按需检索。
  • 局部重编译：修改一个模块时，只重测受影响任务族。
  • 变更指纹：每条 edit 注明目的、影响面、依赖章节和预期指标。
  • 淘汰机制：对连续无收益或导致冲突的章节降级、合并或删除。
  • Champion-Challenger：小改动长期影子比较，避免短窗误判。
不要为了 1% 平均分承受结构性风险：如果一次 300 token 的 edit 只让平均分从 74% 到 75%，但在某个核心任务族引入新的重复循环，应优先拒绝或继续观察。自进化系统的目标不是每次都找到改进，而是避免把噪声和局部优化固化成全局债。
结论：20k token 的 Skill 本身就是优化信号。先用模块化减少上下文稀释，再用配对、分层和多次采样评估小效应；无法稳定超过噪声带的 edit，不应进入主干。
09

业界洞察：从 Skill 包、评测框架到进化式 Agent

下面的公开案例不追求覆盖所有产品，而是提取与你五个痛点直接相关的机制：如何管理上下文、如何构造评测、如何用环境反馈进化、如何把 prompt 变成可编译系统。产品实现会持续变化，这里关注可迁移的架构模式。

案例 1

Anthropic Agent Skills：渐进式披露的 Skill 包

Anthropic 的 Agent Skills 把能力组织成包含 SKILL.md、说明、脚本和资源的包。运行时不需要一开始加载所有内容，而是先看到精简元数据，需要时再读取正文或调用脚本。这正好回应“大 Skill 20k+ token”的问题。

可借鉴架构

  • Skill 是文件化、版本化资产，不是不可审计的聊天片段。
  • 元数据、正文、脚本和资源分层加载，减少上下文稀释。
  • 可执行脚本比长篇自然语言更稳定，适合承载检查和固定流程。
启示：不要让 Skill 无限长。把“必须知道”放进入口卡，把“偶尔需要”放进资源，把“必须一致执行”放进脚本或门禁。
案例 2

SWE-agent / SWE-bench：接口与真实仓库评测

SWE-agent 研究了 Agent-Computer Interface 对表现的影响；SWE-bench 用真实 GitHub issue、仓库状态和测试验证模型能否产出可合并补丁。它们共同说明：编程 Agent 的能力很大程度由 Harness、工具接口和评测环境塑造。

可借鉴架构

  • 工具输出要短、可定位、可比较，避免把整个文件塞给模型。
  • 任务包绑定 repo commit、测试 patch 和通过/失败判据。
  • 评测不只看最终文本，还要看能否通过真实仓库测试。
启示：给编程 Agent 设计“可观察、可操作、可纠错”的界面；bad case 最终要落到可执行的任务包上。
案例 3

OpenAI Evals / LangSmith / Braintrust：评测基础设施化

OpenAI Evals 把模型和系统评测抽象成数据集、运行器与评分器；LangSmith、Braintrust、Langfuse 等平台把 trace、数据集、实验、人工标注和线上监控组合成闭环。它们的核心价值是让“改了一个 prompt 是否更好”变成可比较实验。

典型数据流

  1. 线上 trace 自动采样，生成候选数据集。
  2. 人工标注、批评模型和程序化判据共同打标。
  3. 候选版本在相同数据集和运行配置上重复实验。
  4. 实验结果带版本、指标和置信信息归档。
启示：评测系统要和运行时同等对待，否则每轮 Skill 修改都会退化成主观判断。
案例 4

DSPy：把 Prompt 组合成可编译程序

DSPy 把 LLM 调用写成签名、模块和流水线，再根据指标自动优化 prompt、示例或配置。这改变了“手改一句话”的迭代方式：优化目标、数据、模块和指标成为一等公民。

可借鉴架构

  • 声明式定义输入输出，而不是把所有规则硬编码进 prompt。
  • 用统一 metric 编译或搜索流水线配置。
  • 把 Skill 拆成可组合模块，避免单一巨型 prompt。
启示：Skill 优化器应提交“模块级变更 + 预期指标 + 实验证据”，而不是一次性重写整个说明书。
案例 5

Voyager：环境反馈驱动的 Skill Library

Voyager 在 Minecraft 中通过自动课程、环境反馈、迭代提示和可执行技能代码构建终身学习 Agent。失败不是终点，而是下一轮课程和技能检索的输入。

闭环映射到 SDD

  • 自动课程 → 从失败簇生成练习任务包。
  • 环境反馈 → 编译、测试、运行和 review 结果。
  • 技能库 → 可复用的脚本、检查表和流程模块。
  • 检索 → 新任务根据语义找到相关 Skill。
启示：Skill 库不只存成功经验，也要存失败模式和“何时不要使用”的反例。
案例 6

AlphaEvolve：可执行评价器驱动的进化搜索

DeepMind 的 AlphaEvolve 用 LLM 提出程序修改，用自动评价器筛选候选，并通过进化式数据库保留高质量方案。它的重点不是模型自由发挥，而是让可计算的评价函数约束搜索。

与 SDD Harness 的对应

  • 变异候选 = Skill / prompt / workflow patch。
  • 评价器 = 测试、lint、基准、成本、安全和人工规则。
  • 种群管理 = 多个 challenger，而非只保留当前版本。
  • 淘汰 = 无法超过噪声带或破坏护栏的变更。
启示：进化式优化需要高质量评价器。评价器弱，进化只会快速找到刷分技巧。
10

落地路线：90 天把自进化做成工程系统

不建议第一步就让 LLM 大规模重写 Skill。更稳的路径是先让 Harness 变成可测量系统，再逐步开放自动生成、自动评测和自动发布。

0-30 天

先建立证据链

  • 定义 Run Envelope：模型、Skill、Prompt、工具、依赖、门禁版本。
  • 把工具调用、命令、测试、审批、用户动作 Span 化。
  • 接入硬失败和用户回滚 / 大幅修改 diff 信号。
  • 选出 20-50 个代表性任务，建立小回归集。
  • 测量当前版本的噪声带，不急着改 Skill。
31-60 天

把 bad case 变成资产

  • 按失败签名、模块、任务族和用户动作聚类。
  • 加入 LLM Critic、风险分和人工抽检队列。
  • 为高频失败生成最小 repo fixture 和反例。
  • 把可静态化的问题转成 lint/test/gate。
  • 为每个高频 Skill 写 Contract 和分层评测。
61-90 天

开放受控自进化

  • 建立候选 patch、实验记录、指标和版本说明。
  • 支持 old / new / off 的反事实 Harness 实验。
  • 引入 Train / Dev / Frozen Test / Out-of-Time 分层。
  • 上线 shadow、小流量灰度、自动回滚。
  • 保留 Champion-Challenger 长期比较。

推荐的最小技术栈

层能力可选用型 / 实现
观测Span、trace、指标、日志、版本标签OpenTelemetry 风格事件模型，或 LangSmith / Langfuse / Braintrust
证据库轨迹、快照、diff、测试、反馈、标注对象存储 + 版本化数据库 + 内容哈希
任务包repo fixture、断言、输入输出、反例、预算Git repo 模板 + Docker/容器 + 测试 runner
实验多版本运行、配对比较、指标汇总CI job + experiment registry + 统计报告
发布shadow、canary、护栏、回滚feature flag + skill registry + release controller
优化器生成候选 Skill / Prompt / Gate patchLLM proposer + critic + 人工审批

反模式清单

只存聊天记录缺少版本、环境和工具状态，无法归因。
只看测试是否变绿会漏掉需求偏差、过度工程、安全与维护性问题。
让模型直接重写大 Skill改动面不可控，回归和冲突难以定位。
同一验证集反复选版本分数持续虚高，线上表现下滑。
用单次成功下结论模型随机性会把噪声误判成收益。
只优化 LLM 裁判分数容易刷解释、格式和表面质量。
所有 Skill 无条件常驻上下文重要指令被稀释，成本和冲突上升。
发布后不观察长期影响后续 hotfix、回滚和用户信任变化才是真实代价。
最终判断：SDD Harness 的护城河不是某条神奇 prompt，而是“真实轨迹 → 可检验任务包 → 因果归因 → 系统级实验 → 受控发布 → 长期监控”的复利系统。模型负责提出假设，工程系统负责让正确假设留下来。
