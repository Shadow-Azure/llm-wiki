03 · 可观测性 / LoongSuite

LoongSuite

阿里云 2025 年 8 月开源的 AI 时代可观测数据采集套件（读作“龙-甜”）。它回答三个问题：AI Agent 的钱花到哪去了？出了问题卡在哪一步？谁来审计 agent 干了什么？主线路线是：非侵入采集 → 统一语义 → 多端消费，全程贴着 OpenTelemetry 标准。

LoongCollector 主机采集Java / Go / Python / JS 探针Pilot 端侧采集GenAI 语义规范OTel 生态
01

它想解决什么问题：从一次“踩坑”说起

想象一个常见场景：你的团队用 Claude Code / Cursor 改代码，用 Dify 搭客服机器人。某天机器人回答开始变慢、变贵，还时不时答非所问。你想查——然后发现根本无从下手。这就是 LoongSuite 针对的四类困境。

问题 1

黑盒决策，链路不可见

一个 agent 任务内含 10+ 轮“推理→调工具→反思”循环。传统监控只看到几个 HTTP 请求，看不到每一轮里模型想了什么、调了哪个工具、哪一步开始跑偏。

问题 2

Token 黑洞

多轮对话的中间过程消耗惊人：循环试错、上下文越滚越大、反复确认的“过度谨慎”，甚至死循环。账单暴涨，却说不清钱烧在哪一轮。

问题 3

数据各说各话

Claude Code、Cursor、Qoder 的数据格式、存储位置、记录粒度都不同。想横向比较“哪个 agent 更适合我们”，没有统一口径，只能凭感觉站队。

问题 4

端侧是盲区

编程 agent 跑在开发者本机：数据散落在 IDE 历史、本地 SQLite、session 日志里。传统探针全都是面向服务器的，完全够不着。

02

它的总体思路：三层采集 + 一层语义

LoongSuite 不是单一工具，而是一套组合拳：主机层的 LoongCollector 收机器级数据，进程层的语言探针收应用内部数据，端侧的 Pilot 收本机编程 agent 数据；底下垫一张统一语义规范，让所有数据说同一种“普通话”，最后用标准 OTLP 协议流向任意后端。

组件管什么一句话记忆
LoongCollector主机上的日志/指标/链路/Profile，含 eBPF 进程外采集整台机器的“总水管工”
Java / Go / Python / JS 探针应用内部的函数调用、LLM 调用、token 用量——全部零改码给代码装“行车记录仪”
Pilot本机编程 agent（Claude Code/Codex/Cursor/Qoder）的会话、工具调用、成本开发者电脑上的“监控摄像头”
GenAI 语义规范统一字段名和层级结构（session→turn→step、token 级）让所有数据说“普通话”
03

它是怎么解决的：四个关键方法

LoongSuite 的设计哲学就一句：“适配 Agent，而不是让 Agent 适配你”。闭源产品改不了、业务代码不该改、标准生态不能绕——四个方法分别对应这三种约束。

方法一：非侵入采集——不同语言，不同“下手”时机

方法二：统一语义——让所有数据说“普通话”

采集到数据只是第一步。LoongSuite 把阿里+蚂蚁内部实战沉淀的 GenAI 语义规范开源：每个事件都带标准字段，光看字段名就能还原现场。官方给过一个真实 Claude Code 事件的例子：

字段（节选）值（示例）它在回答什么
gen_ai.agent.typeclaude-code谁干的
gen_ai.session.id → turn.id → step.id8e06…:t1:s3哪次会话 → 第 1 轮对话 → 第 3 个推理步
gen_ai.tool.name + argumentsBash: "ls /workspace/docs/"干了什么、参数是什么（安全审计关键）
gen_ai.tool.call.idtoolu_vrtx_0115…把“发起调用”和“返回结果”配成对
trace_id / span_id / parent_span_id09f1… / dc68… / d5af…把整场任务串成一棵调用树
杠杆效应：字段统一后，同一条 SQL 吃遍所有 agent——比如“揪出单请求超 5 万 token 的会话”“统计每个 agent 最常用的 10 个工具”，不用关心数据来自 Claude Code 还是 Cursor。新接一个 agent，下游的看板、告警、查询自动生效。

方法三：端侧 Pilot——给本机 agent 装“摄像头”

方法四：语义规范的“工程化外壳”——GenAI Utils

如果每个框架的探针都各自实现“建 span、挂字段、记指标”，规范一升级就要改 N 处。GenAI Utils 把这些样板逻辑收进一个公共 Handler：探针只负责“从框架里抽数据”，输出规范的事一律交给公共层——规范升级改一处，所有探针自动生效。

04

示例：从安装到看板，Pilot 的完整一遍流程

以官方博客的实操为例：团队想让 Claude Code 的使用变得可查。全程约 1 分钟，中间不改任何使用习惯。

第 1 步：一行命令安装

执行 installer.sh 并填上 SLS（日志服务）参数。脚本自动下载、部署到 ~/.loongsuite-pilot/、给 Claude Code 装 hook、拉起后台进程。想看调用树再加 --collect-trace true。

第 2 步：自动发现，静默采集

Pilot 扫描本机，发现已安装的 Claude Code / Cursor / Codex / Qoder，按各自的声明配置自动注入采集能力。之后你照常干活，它不打扰。

第 3 步：本地看板确认“在流数据”

loongsuite-pilot monitor start 打开 127.0.0.1:8765：每个 agent 的事件数、最近活跃时间、上报成功率、Pilot 自身资源占用，一眼确认采集正常。

第 4 步：看一条原始事件

本地 JSONL 里躺着标准事件。比如一条 tool.call：session :t1:s3 说明是“第 1 轮对话第 3 步”，工具 Bash、参数 "ls docs/"，配对的 tool.result 用同一 call id——现场完整还原。

第 5 步：用 SQL 提问

数据进 SLS 后直接写 SQL：“某人过去 7 天消耗多少 token”“每个 agent 的 Top 10 工具及平均耗时”“单请求超 5 万 token 的异常会话”——同一套 SQL 对所有 agent 通用。

第 6 步：回答四个业务问题

ROI（任务完成率、token 效率比、人机协作比、自修正率）；选型（同一任务交给三家 agent 的行为差异）；成本（识别三类 token 黑洞）；安全（六层审计 + 敏感信息自动脱敏）。

结果：从“凭感觉用 agent”变成“用数据管理 agent”。同一任务实测三家（Claude Code / Cursor / Qoder）：Claude Code 总时长最短、Bash 风格像终端老手；Cursor 单轮思考最深、产出最细但最慢；Qoder token 最省、小步快跑。差异之前全被“体感”掩盖。

07

冷思考：它没有解决的问题

边界 1

采集 ≠ 治理

LoongSuite 负责“把数据拿全、拿准”，但 ROI 提升需要组织配套动作（选型决策、流程改造）。数据只是必要条件。

边界 2

闭源 agent 的依赖

端侧采集走 hook/SQLite/session 旁路，agent 一改存储格式就可能断流——这是“适配而非改造”路线的固有代价，靠声明式配置降低维护量但不消除。

边界 3

标准话语权博弈

语义规范先落在厂商品牌下、再择机回馈上游。若上游演进方向分叉，双轨期会产生迁移成本（官方已用“继承上游 Handler”的兼容设计对冲）。

边界 4

开源与商业的灰度

部分能力先商业版（ARMS）后开源，文档中的演示与开源版存在时间差。评估时需逐项核对开源版可用性。
