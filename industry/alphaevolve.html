Case 06 · Evolutionary Coding Agent

AlphaEvolve

AlphaEvolve 是 DeepMind 描述的进化式编码 Agent：LLM 负责提出程序修改，评价器负责判断候选是否正确、更快或更省资源，进化式数据库负责保留多样且高质量的父代。它把“模型猜一猜”变成“可执行评价约束下的搜索”。

关键词：进化搜索LLM 变异可执行评价器种群管理防 reward hacking
01

它想解决什么问题

很多算法和系统优化问题有一个共同特点：目标可以用代码衡量，但搜索空间远超人类直觉。LLM 一次生成常常很惊艳，也可能悄悄犯错；单次采样也无法证明一个方案真的更好。

问题 1

搜索空间巨大

循环顺序、分解方式、缓存策略、并行结构组合极多，人不可能穷举。

问题 2

单次生成不可靠

模型可能写出看似合理但边界错误、性能更差或依赖特定硬件的程序。

问题 3

指标容易被误解

只看运行时间，可能牺牲正确性；只看代码短，可能失去泛化。

问题 4

评价本身有噪声

机器负载、缓存状态、并行度都会让同一程序的耗时波动。

问题 5

局部最优

只保留当前最好的候选，很快会停止探索，失去多样性。

问题 6

候选不可追溯

不知道哪个父代、哪条 mutation、哪组评价结果产生了新方案。

适用前提：必须有足够好的评价器。如果正确性和性能都能被程序验证，进化式搜索才有意义。
02

它是怎么解决的

AlphaEvolve 的模式可以抽象成：种子程序 → LLM 变异 → 沙箱评价 → 多目标打分 → 种群更新 → 迭代循环。

关键设计

设计作用如果没有它会怎样
种子程序给搜索一个可运行的起点。模型从空白生成，难以复用已有工程上下文。
可执行评价器客观判断候选是否更好。只能靠人眼或模型主观打分，容易被表面质量误导。
沙箱执行隔离危险代码并限制资源。死循环、非法访问或高成本实验会影响系统。
多目标评分同时看正确性、速度、内存、复杂度。候选刷一个指标牺牲其他指标。
多次测量减少计时噪声。把偶然快的候选误判为优秀。
进化式数据库保留父代、分数、血缘和多样方案。搜索过早收敛，也无法解释来源。
精英与探索平衡既保留好候选，也尝试新方向。系统反复微调同一局部。
03

示例：搜索更高效的矩阵乘法实现

矩阵乘法是典型问题：正确性可以精确验证，乘加次数、耗时和内存也能测量；但不同分块、循环顺序、并行和缓存策略的组合非常多。

第 1 步：准备种子程序

先放入一个正确但普通的分块矩阵乘法实现。它能在所有测试用例上通过，性能作为 baseline。

第 2 步：定义评价器

第一优先级是正确性：随机矩阵、单位矩阵、奇异矩阵、极小值和极大值都必须在容差内匹配。第二层是乘加次数、P50/P95 耗时、峰值内存。

第 3 步：生成初始种群

用多个 LLM 提议对分块大小、循环顺序、临时数组和边界分支的修改。每个候选都记录父代和 diff。

第 4 步：沙箱执行

每个候选在受限环境编译和运行。禁止网络、限制 CPU/内存/时间，超过预算直接淘汰。

第 5 步：发现错误候选

候选 A 把分块改大，速度快 8%，但在非方阵用例数值误差超标。评价器标记 invalid，不进入精英。

第 6 步：发现性能候选

候选 B 调整循环顺序并复用中间块，正确性全过，P95 耗时下降 12%，内存增加 3%。进入种群。

第 7 步：测量噪声

由于机器波动，每个最终候选重复跑多轮，取中位数和尾部表现。B 相对 baseline 的提升仍然稳定。

第 8 步：继续变异

下一轮以 B 和若干多样性候选为父代，尝试不同分块策略和边界展开。评价器继续淘汰错误和退化方案。

第 9 步：输出可审计结果

最终方案附带来源 diff、父代、测试矩阵、性能曲线和失败候选。不是只给一个“更快代码”。

效果：LLM 的创造性被保留，但每个候选必须穿过正确性、性能、资源和稳定性四道关。最终留下的不是“听起来聪明”，而是“测得更好”。
04

实际会遇到的问题与处理方式

阶段问题表现解决方法
生成非法代码语法错、类型错、API 不存在。静态检查 + 编译错误反馈，让 LLM 修正或淘汰。
生成过大重写无法判断哪个变更带来收益。限制 patch 范围，要求局部可测变异。
评价正确性漏洞常见用例通过，边界失败。随机测试、极端输入、不变量和金标准对比。
评价性能测量噪声同一程序时间波动大。多次运行、预热、中位数/P95、控制机器负载。
评价reward hacking减少计算但结果不正确。正确性硬门槛；禁止修改测试；审查输出分布。
搜索局部最优所有候选都很相似。保持多样性父代，允许探索性变异。
搜索成本爆炸候选太多，每次评价很贵。先便宜过滤，再昂贵测试；限制代数和并发。
工程不可复现换机器后优势消失。锁定硬件/依赖/输入，保存原始日志和环境。
最大陷阱：评价器弱，进化就变成刷分器。AlphaEvolve 模式只适合能够把目标写成可靠代码判据的问题。
05

对 SDD Harness 的启示

启示 1

LLM 是 proposer

让它提出 Skill / prompt / gate patch，不要让它既生成又自我宣布成功。

启示 2

评价器是护城河

测试、成本、安全、循环率和人工接受率应组成硬门禁。

启示 3

保留种群和血缘

不要只维护一个 current prompt；challenger 能帮助观察长期稳定性。

映射关系：程序 patch 对应 Skill/Workflow patch；正确性测试对应 SDD 门禁；性能测量对应 token/时延/人工成本；进化数据库对应版本化 Skill 库与实验 registry。
