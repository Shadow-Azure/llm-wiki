Case 03 · Evaluation Infrastructure

OpenAI Evals · LangSmith · Braintrust

这三个方案的共同目标是把“我觉得新 prompt 更好”变成“同一数据集、同一运行协议、同一评分口径下，新版本确实更好”。OpenAI Evals 偏开放评测框架，LangSmith 偏 trace 加实验平台，Braintrust 偏产品化评测与实验工作流。

关键词：数据集ScorerExperimentTrace线上监控
01

它们想解决什么问题

LLM 应用早期常见状态是：prompt 散落在代码里，测试靠人肉看几条样本，线上坏例靠截图传播。这类方式无法支撑持续迭代。

问题 1

主观评分不可复用

今天说“回答不错”，明天另一人认为格式不合格。没有评分器，就无法比较版本。

问题 2

样本不代表分布

团队常用 5 条自己造的例子。上线后真实用户输入更长、更歧义、更脏。

问题 3

坏例无法回溯

只保存最终答案，看不到检索、工具、模型版本和中间决策。

问题 4

版本回归难发现

某类问题变好了，另一类悄悄变差；没有分层指标就看不出来。

问题 5

多人协作困难

产品、算法和工程各自保存表格，实验无法复用和审计。

问题 6

线上漂移无人察觉

用户问题、模型版本或工具结果变化后，质量缓慢下降。

02

它们是怎么解决的

三者实现方式不同，但都能抽象成同一个闭环：Trace → Dataset → Run → Scorer → Experiment → Monitor。

三个方案的定位

方案更像什么主要贡献适合场景
OpenAI Evals开放评测框架用统一结构描述任务、样本、模型调用和评分器。建立可复用、可开源、可代码化管理的评测。
LangSmithLLM 应用观测与评测平台嵌套 trace、数据集、实验、反馈、线上监控。调试复杂 Agent 和 RAG，追踪每个工具调用。
Braintrust产品化实验与评测平台实验、数据集、评分器、日志和协作界面。产品和工程一起管理 prompt/Agent 版本。

评分器应分层

层例子优点风险
硬校验JSON schema、SQL 可执行、引用存在、价格正确。便宜、稳定、可复现。覆盖不了语义质量。
规则/启发式长度、格式、禁止词、必须包含章节。能快速拦截明显错误。阈值过严会误伤。
LLM judge按 rubric 评价完整性、事实性、帮助性。可覆盖软指标。偏长答案、位置偏差、容易被讨好性文本骗过。
Pairwise judge新版本 A 对比旧版本 B。适合相对改进。要控制顺序和长度偏差。
人工抽检高风险样本、争议样本、随机样本。校准自动评分器。贵、慢、标准会漂移。
03

示例：优化一个客服退款 Agent

假设 Agent 要根据订单状态和退款政策决定“自动退款、转人工、请用户补材料”。现在要从 v1 迭代到 v2。

第 1 步：采集真实 trace

每个请求记录用户问题、订单状态、政策检索片段、工具调用、模型输出、后续人工动作。发现 40 条被客服推翻，20 条用户重复追问。

第 2 步：构建分层 Dataset

拆成四层：标准退款、跨币种、欺诈嫌疑、政策歧义。每层都有输入、期望动作、关键理由和禁止事项。真实坏例进入挑战集。

第 3 步：定义评分器

硬校验检查是否调用了正确订单接口；规则检查是否输出合法动作；LLM judge 按 rubric 评价政策引用和解释；人工抽检校准 judge。

第 4 步：运行实验

在相同数据集上跑 v1 和 v2，各重复多次。记录总分、每层通过率、平均 token、时延和工具调用次数。

第 5 步：分析失败簇

总分从 78 到 84，但“欺诈嫌疑”层从 70 降到 55：v2 更倾向自动退款。这个回归阻止直接发布。

第 6 步：加入护栏

v2 增加规则：金额高、订单新、账号异常时必须转人工。重新实验后，总分到 83，高风险层回到 78。

第 7 步：上线监控

先 shadow 跑真实流量，再 5% 灰度。监控人工推翻率、重复追问率、退款金额异常和时延。劣化时回滚。

效果：团队不再讨论“v2 看起来更强”，而是能回答：在哪层任务提升、哪层回退、成本变化多少、上线后用哪些护栏判断失败。
04

实际会遇到的问题与处理方式

阶段问题表现解决方法
数据集数据泄漏优化 prompt 时反复看过测试样本。Train/Dev/Frozen Test 分离；按语义和任务去重。
数据集分布偏移旧样本太短、太干净，线上输入复杂。定期从真实 trace 补充；保留长尾和对抗样本。
Trace嵌套断链看不到工具调用和检索结果的关系。统一 trace_id/span_id，记录父子关系和版本。
隐私敏感数据入库手机号、订单、身份信息暴露。入库前脱敏、权限分级、保留最小字段。
评分judge 偏长答案冗长回答得高分。长度控制评分；pairwise 打乱顺序；人工校准。
评分只看平均分核心任务回退被简单任务掩盖。按风险、任务族、用户类型分层报告。
实验单次采样噪声涨分 2% 无法判断是否真实。多次运行、配对比较、置信区间、设置最小差异。
上线验证集过拟合离线很好，线上回退。冻结测试、时间外测、shadow、canary 和回滚。
Goodhart 风险：一旦团队只优化 judge 分数，模型可能学会写出更漂亮的解释而不是更正确的行动。自动分数必须与硬校验、业务护栏和用户后续行为一起看。
05

对 SDD Harness 的启示

启示 1

Trace 是第一公民

没有嵌套工具和版本信息，就很难从线上坏例回到根因。

启示 2

评分要混合

硬校验保底线，judge 覆盖软质量，人工只做校准和仲裁。

启示 3

实验要可审计

每次比较都保存数据集版本、prompt 版本、模型版本、运行参数和原始输出。

最小落地：先做一个 50 条任务的分层集 + 5 个硬校验器 + 1 个 LLM judge + 1 个实验报告。不要等完美平台才开始评测。
