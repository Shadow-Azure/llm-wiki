Case 04 · Programming, Not Prompting

DSPy

DSPy 把 LLM 应用写成“签名 + 模块 + 指标 + 优化器”的声明式程序。开发者描述输入输出和成功标准，优化器在数据上搜索更好的 prompt、示例和配置。它的口号可以通俗理解成：不要手搓咒语，要编译程序。

关键词：SignatureModuleMetricOptimizerPipeline Compile
01

它想解决什么问题

传统 prompt 工程有很多隐性知识：语气、格式、few-shot 示例、思维链、输出 schema、重试策略都混在一大段文本里。一旦任务、模型或上下文变化，就要重新调一遍。

问题 1

Prompt 脆弱

换一个模型、换一个措辞，甚至换示例顺序，结果都会变化。

问题 2

流水线耦合

检索、推理、总结、评分各自都有 prompt。改上游格式，下游就崩。

问题 3

优化缺目标

团队经常说“回答更好一点”，却没有机器可执行的 metric。

问题 4

示例选择靠感觉

few-shot 常用三个漂亮例子，但不代表任务分布，也不一定适合新模型。

问题 5

手工搜索太贵

模板、指令、示例、模型参数组合太多，人不可能枚举。

问题 6

复现和迁移难

prompt 在聊天里被反复改，最后没有人知道哪个版本对应哪个分数。

核心思想：把“怎么向模型表达”和“任务成功是什么”分开。程序定义结构，指标定义目标，优化器负责搜索表达方式。
02

它是怎么解决的

DSPy 的关键不是某个神奇 prompt，而是把 LLM 调用变成可编译系统。下面是一条典型的优化链路。

核心抽象

抽象通俗解释例子
Signature声明一个 LLM 步骤的输入输出和语义，而不是写死全文 prompt。question, context -> answer, citations
Module可组合的流水线组件。检索器、生成器、总结器、评分器。
Metric判断一次输出是否成功的函数。答案匹配、引用存在、JSON 合法、裁决模型评分。
Optimizer根据指标在候选配置中搜索。筛选有效 few-shot、改写指令、优化模块配置。
Compiled Artifact优化后的程序和提示配置。带版本号的 pipeline，而不是散落聊天记录的 prompt。
与普通 prompt 模板的区别：模板只是静态文本；DSPy 把静态文本当成可搜索参数，并且用任务指标决定保留哪个版本。
03

示例：构建多跳问答助手

用户问：“A 公司 2024 年收购的 B 公司，其创始人后来创办了什么公司？”这需要先查收购，再查创始人，再查新公司。单轮 prompt 很容易漏步骤。

第 1 步：定义签名

第一个模块声明：question -> search_query。第二个模块声明：question, context -> answer, evidence。程序不关心最终 prompt 具体怎么写。

第 2 步：组合模块

Pipeline 是：生成检索词 -> 调用搜索 -> 合并片段 -> 生成答案。每一步都是独立模块，可以单独替换。

第 3 步：准备小数据集

准备 100 道多跳问题。训练集 60 道，验证集 20 道，测试集 20 道长期冻结。每题有标准答案和支持文档。

第 4 步：定义指标

答案正确得 1 分；缺少证据扣 0.4；引用文档不支持答案得 0；格式非法直接失败。指标不只是“文字相似”。

第 5 步：先跑 baseline

未优化程序在验证集得分 52%。失败模式包括：只查 A 公司、忽略创始人、编造公司名、没有引用。

第 6 步：优化器筛选示例

优化器在训练集上运行程序，保留通过指标的轨迹，把它们转成 few-shot 示例。例如展示“先查收购，再查创始人，再查新公司”的完整推理。

第 7 步：编译并验证

优化后的 pipeline 在验证集从 52% 到 68%。再在冻结测试集评估，得到 65%。团队记录模型、数据版本、优化器参数和 metric。

第 8 步：失败归因

剩余失败里，40% 是检索没有第二跳，30% 是证据不支持答案。下一步不是继续改 prompt，而是改进检索和证据校验。

效果：模型从“一次性回答”变成结构化流程；优化器用可执行指标选择更有效的指令和示例；版本变化有实验记录。
04

实际会遇到的问题与处理方式

阶段问题表现处理方式
指标metric 可被刷分模型输出很长但答案含糊。加入正确性、证据、格式、简洁度多个判据。
指标exact match 太苛刻语义相同但措辞不同被判失败。硬答案 + alias + LLM judge + 人工仲裁。
数据训练集太小few-shot 示例不代表分布。分层采样，覆盖难例、边界例和负例。
数据验证集被反复使用分数持续虚高。分开 dev/test；限制访问次数；保留冻结集。
优化成本过高每个候选都在全量集上跑。先小集筛选，再Top候选全量评估。
优化过拟合 few-shot训练题好，新题差。保持示例多样性，测试分布外问题。
流水线上游格式漂移检索 JSON 变了，答案模块崩。签名 + schema 校验 + 失败重试。
复现外部检索变化同一程序分数波动。评测时缓存检索结果；线上再测真实检索。
不要误用：DSPy 不能把坏 metric 变成好系统。如果指标只看关键词命中，优化器会学会堆关键词，而不是学会多跳推理。
05

对 SDD Harness 的启示

启示 1

Skill 要有接口

每个 Skill 步骤声明输入输出，方便组合、替换和回归。

启示 2

优化要有 metric

先定义“什么算修好、什么算好的计划”，再让模型搜索表达方式。

启示 3

小步编译

不要一次重写 Skill；把指令、示例、流程和门禁当成可搜索参数。

落地模板：为 Skill 写 signature、最小数据集、metric、baseline 报告、优化候选和冻结测试。每次优化后记录“哪个模块变了、为什么、代价是什么”。
